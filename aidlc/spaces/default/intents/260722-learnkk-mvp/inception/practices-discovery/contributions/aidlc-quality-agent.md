## Contribution

리드 초안(team-practices.md, discovered-rules.md)의 **Testing Posture**를 품질 관점(테스트 자세·커버리지 도구·CI 품질 게이트·테스트 패턴·인터뷰 미결 사항)에서 검토했다. 증거는 greenfield라 코드/CI 증거가 없고 org.md 기본값 + project.md 결정에서 추론된 상태다.

**전반 평가: 방향은 건전하나 파일럿 현실과 정합성에서 몇 가지를 재조정할 것을 권고한다.**

1. **80% 라인 커버리지 목표의 현실성.** 초안은 "mvp 스코프이지만 enterprise 테스트 자세 채택"으로 80%를 하드 제약(ALWAYS)으로 승격했다. 전담 QA 없는 4~6명 풀스택 파일럿에서 **전 코드 획일적 80% 라인 커버리지를 머지 블로킹 하드 게이트로 두는 것은 속도 저하 위험**이 크다. 특히 라인 커버리지는 "의미 없는 assertion으로 채운 80%"를 허용해 품질 착시를 낳는다(핵심 원칙 5). 파일럿 목표(출시 속도·좁은 범위)와 상충한다.
   - 권고: **위험 기반 차등 커버리지**. 핵심 도메인 로직(선착순 참여·정원 마감, 증빙 기반 출석 인증, 최종 보고서/운영 지표 집계, 인증/인가)은 높은 커버리지·강한 assertion을 요구하고, DTO·getter/setter·설정·단순 UI 마크업은 제외한다. 80%는 "머지 차단 하드 게이트"가 아니라 **핵심 모듈에 적용되는 팀 목표치**로 두는 편이 파일럿에 맞다. 하드 제약 승격 여부는 인터뷰에서 인간이 결정해야 한다.

2. **도구 선택(Jest/RTL + JUnit5/MockMvc)은 스택에 적합.** 프론트 Jest/React Testing Library, 백엔드 JUnit 5 + MockMvc는 표준적이고 학습 곡선이 낮아 파일럿에 적절하다. 다만 두 축이 커버하지 못하는 영역이 있다:
   - **동시성**(선착순/정원)은 MockMvc 단위 슬라이스로는 검증 불가 — 실제 DB 트랜잭션·락 경합을 태우는 통합 테스트가 필요하다(아래 4).
   - **파일 업로드(출석 증빙)**는 MockMvc의 `MockMultipartFile`로 컨트롤러 계층은 되지만, 저장·검증·이력 보관은 통합 테스트가 필요하다(아래 5).
   - E2E(브라우저) 도구는 초안에 없다. 파일럿에서는 전면 E2E는 생략하되, "핵심 사용자 플로우 1~2개 스모크"만 둘지 인터뷰에서 결정 권고.

3. **통합 vs 단위 균형이 명시되지 않음.** 초안은 "단위·통합 테스트 작성 책임"만 언급하고 비율/우선순위를 정하지 않는다. 이 프로젝트의 리스크는 대부분 **동시성·데이터 정합성·파일 처리**에 있어 순수 단위 테스트로는 못 잡는다. 피라미드를 지키되(핵심 원칙 2), **정원/출석/집계 경계에는 통합 테스트를 의도적으로 배치**할 것을 권고. `@SpringBootTest` + Testcontainers(실 DB) 또는 최소 H2로 트랜잭션 경계를 검증한다.

4. **선착순 참여/정원 동시성 테스트 데이터·전략이 공백.** 이는 이 파일럿 최대의 정합성 리스크다.
   - 필요: 정원 N에 대해 동시 요청 M(>N)을 던지는 **동시성 테스트**(예: `ExecutorService` + `CountDownLatch`로 병렬 참여 요청), 정확히 N명만 확정·초과분은 거부/대기 처리되는지 검증. 낙관적 락(`@Version`)/비관적 락(`SELECT ... FOR UPDATE`)/유니크 제약 중 어느 전략을 쓰는지에 따라 테스트가 달라지므로 **동시성 제어 전략을 인터뷰에서 확정**해야 테스트를 설계할 수 있다.
   - 테스트 데이터: 정원 경계값(N-1, N, N+1), 동시 진입, 중복 참여 시도를 픽스처/팩토리로 준비.

5. **증빙 기반 출석 인증 테스트가 미정의.** 첨부 즉시 인증되는 흐름(project.md c2, rough-mockups c2)은 검증 포인트가 여럿이다: 허용 파일 타입/크기, 저장 성공, 해당 회차 출석 상태 전이, **증빙 이력 보관**(감사성). 
   - 권고: 정상 업로드 → 출석 인증 → 이력 1건 적재의 통합 테스트 1개를 핵심 회귀로 고정. 파일 제약(타입·크기 상한)은 approval-handoff c1에서 INCEPTION 확정 대상이므로, 확정 전까지 경계 테스트는 placeholder로 둔다.

6. **전담 QA 없음 → 프로세스로 보완.** 개발자가 자기 코드 테스트를 작성하는 구조이므로, 품질 안전망은 **PR 리뷰 시 테스트 리뷰 포함** + **결함마다 재현 테스트 선작성**(핵심 원칙 3) 관행으로 보완할 것을 권고. discovered-rules에 "핵심 도메인 로직 변경 시 테스트 동반" 정도의 완화된 규칙이면 충분하고, 획일적 80% 하드 게이트보다 파일럿에 현실적이다.

7. **CI 품질 게이트 정합성.** discovered-rules의 "ALWAYS 머지 전 CI에서 린터·테스트 실행, 실패 시 블록"은 타당하다. 다만 CI 도구가 미결(evidence 미결 1)이고 로컬 서버 배포 환경이라, **커버리지 리포트 도구**(프론트 Jest `--coverage`, 백엔드 JaCoCo)와 게이트 임계 적용 여부를 인터뷰에서 함께 확정해야 "80% 게이트"가 실제로 강제 가능한지 결정된다.

## Positions

- **P1 (커버리지 하드 게이트 완화 권고):** "ALWAYS 최소 80% 라인 커버리지 유지"를 전역 하드 제약(discovered-rules Mandated)으로 두는 데 **반대**한다. 대신 (a) 핵심 도메인 모듈 대상 팀 목표치 80%, (b) 전역 머지 차단은 "린트 + 테스트 그린"까지로 완화를 권고. 최종 하드 제약 승격 여부는 인터뷰 인간 판단.
- **P2 (위험 기반 테스트 우선순위):** 커버리지 총량보다 **선착순/정원 동시성, 증빙 출석 인증, 집계(운영 지표·최종 보고서), 인증/인가** 4개 핫스팟에 통합 테스트를 집중 배치하는 것을 지지.
- **P3 (도구):** Jest/RTL + JUnit5/MockMvc 채택 지지. 추가로 백엔드 통합 테스트에 **H2 또는 Testcontainers** 도입 여부 결정 필요, 프론트/백 **커버리지 리포트 도구(Jest coverage / JaCoCo)** 명시 필요.
- **P4 (피라미드):** 단위 다수 + 핫스팟 통합 소수 + E2E는 스모크 1~2개(선택). ice-cream-cone 회피.

### 인터뷰 미결 질문(품질 렌즈)
1. **커버리지 정책**: 80%를 머지 차단 하드 게이트로 강제할지, 핵심 모듈 팀 목표치로 완화할지? 라인/브랜치/도메인 기준?
2. **동시성 제어 전략**(정원/선착순): 낙관적 락(@Version) vs 비관적 락 vs DB 유니크 제약 — 테스트 설계의 전제. (동시성 테스트를 CI에 상시 포함할지도 결정)
3. **백엔드 통합 테스트 인프라**: H2(경량) vs Testcontainers(실 DB 근접) — 파일럿 속도 vs 정합성 신뢰도 트레이드오프.
4. **증빙 파일 제약**(타입/크기 상한) 확정 시점 — approval-handoff에서 INCEPTION 이월된 미결이므로 경계 테스트 확정 시점 조율.
5. **E2E/스모크 범위**: 파일럿에서 브라우저 E2E를 둘지, 핵심 플로우(로그인→대시보드→코호트 참여→출석 인증) 스모크만 둘지.
6. **테스트 데이터 전략**: 팩토리/픽스처/시드 방식과 동시성 테스트용 부하 데이터 준비 방법.
7. **결함 회귀 정책**: "결함마다 재현 테스트 선작성"을 팀 관행으로 확정할지.
