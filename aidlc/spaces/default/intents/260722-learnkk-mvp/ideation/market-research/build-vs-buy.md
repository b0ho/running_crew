# Build vs Buy Assessment — LearnKK (사내 멘토링 통합 플랫폼)

> Ideation · market-research 단계 산출물
> 상위 입력: `intent-capture/intent-statement.md` (사내 멘토링 과정 통합; 차별화 = 사내 흐름 맞춤)
> 근거: market-research-questions.md (Q5=Build, Q2=상용 가격 부담, Q1=오픈소스 참고, Q4=차별화=지급 기록증)

## 평가 기준 & 점수 (Evaluation)

점수: Build 유리 +2 ~ Buy 유리 -2

| 요인 | 판단 | 점수 |
|---|---|---|
| 핵심 차별화 여부 | 산발 과정의 통합 관리·사내 멘토링 흐름 맞춤은 범용 제품이 못 다룸 → Build | +2 |
| 출시 속도 | 상용/오픈소스가 빠르지만, 요구가 단순·소규모라 자체 개발도 감당 가능 | 0 |
| 3년 총비용 | 상용은 사내 소규모에 가격 부담(Q2=A); 자체 개발은 초기 개발비 존재 | +1 |
| 커스터마이즈 필요도 | 사내 멘토링 흐름 맞춤 필요 높음 → Build | +2 |
| 데이터 민감도 | 특별 규제는 없으나(Q3=C) 직원 데이터라 자체 보유가 안전 | +1 |
| 유지보수 부담 | 자체 개발 시 지속 책임 발생 (Buy면 벤더가 처리) | -1 |
| 팀 역량 | 사내 개발로 진행 전제 (Q5=A) | +1 |

합계: **+6 (Build 우세)**

## 결정 & 근거 (Decision & Rationale)

- **결정: Build (직접 개발)** — 사용자 결정(Q5=A)과 정량 평가(+6) 모두 Build를 지지.
- **근거**:
  - 핵심 차별화(산발 과정의 통합 관리·사내 멘토링 흐름 맞춤)는 상용/오픈소스가 그대로 제공하지 않음(competitive-analysis 참조). 증서(수료증·지급 기록증)는 단순 이미지 1장 수준의 부가 산출물로, 차별화 요소가 아님(사용자 확정).
  - 상용 제품은 사내 소규모 도입에 **가격 부담**(Q2=A).
  - 오픈소스는 **참고 기준(baseline)**으로 활용하되(Q1=D) 그대로 채택하지 않고, 필요한 기능만 자체 구현.
  - `intent-statement.md`의 핵심 가치(사내 흐름에 맞춘 통합 관리)를 가장 잘 만족.

## 리스크 & 후속 확인 (Risks & Follow-ups)

- **유지보수 부담**: 자체 개발의 지속 책임. 초기엔 필수 기능(table-stakes)에 집중해 범위를 좁게 유지 권고.
- **오픈소스 참고의 범위**: "참고만 할지 / 일부 컴포넌트를 채택할지"는 application-design 단계에서 확정 필요.
- **확장 시 데이터 정책**: 전사 확장(Q6=B/C) 시 직원 데이터 취급 정책 재확인 (market-trends 참조).
