# Scope Document — LearnKK (사내 멘토링 통합 플랫폼 파일럿)

> Ideation · scope-definition 단계 산출물 · 리드 product (서포트: delivery)
> 상위 입력: `intent-capture/intent-statement.md`, `feasibility/feasibility-assessment.md`, `feasibility/constraint-register.md`
> 근거: scope-definition-questions.md (Q1~Q4)

## 범위 개요 (Overview)

`intent-statement.md`의 목표(산발된 사내 멘토링 과정을 단일 플랫폼으로 통합)를 초기 파일럿 범위로 좁혀 정의한다.
`feasibility-assessment.md`의 GO 판정과 제약(React+Spring·로컬 서버·자체 로그인·빠른 파일럿)을 전제로 한다.

## 사용자 역할 (Roles)

- **멘토(직원)**: 코호트 개설·수정(정원 설정), 공지, 출석 증빙 업로드, 최종 보고서 제출
- **멘티(직원)**: 코호트 탐색·선착순 참여, 진도·출석·공지 확인, 수료증 수령
- **시스템 관리자/운영 담당자**: 정원 마감 시 수동 점검·승인, 운영 지표·증빙 이력·최종 보고서 이력 조회

## In-Scope — Must-have (파일럿 필수)

| ID | 기능 | 비고 (Q1/Q2 반영) |
|---|---|---|
| M1 | 멘토의 코호트 개설·수정 | **정원(capacity)** 설정 포함 |
| M2 | 멘티의 코호트 탐색·참여 | **선착순 자동 참여**(멘토 승인 없음). 정원 마감 시 **시스템 관리자 수동 점검·승인** |
| M3 | 진도·출석 관리 | **멘토가 증빙자료 첨부 업로드 → 출석 인증제**, 증빙 이력 보관 |
| M4 | 코호트 단위 공지 | 외부 미팅 링크 공유 포함(내장 화상 없음) |
| M5 | 자체 계정 회원가입·로그인 | 수집 정보 **이메일·성명·닉네임만** |
| M6 | 수료증·정산서 발급 | 단순 **이미지 1장** 수준. 정산서는 "정산 조건 충족" **메시지** 수준(복잡한 발급/검증 없음) |
| M7 | 최종 보고서 제출 | 멘토/멘티가 코호트 종료 시 최종 보고서 제출 |
| M8 | 운영 지표·이력 조회 | 완주 코스 수·출석/수료율·증서 발급 수 + **증빙 이력·최종 보고서 이력** (Q2=B로 Must 승격) |

## In-Scope — Should-have (여유 시)

| ID | 기능 |
|---|---|
| S1 | 코호트 검색 필터/정렬 개선 |
| S2 | 공지 알림(사내 이메일) |

## Out-of-Scope — Won't-have (이번 파일럿 제외, Q3=A 확정)

- 온라인 결제/정산 처리 (정산은 오프라인; 플랫폼은 조건 충족 메시지만)
- 내장 화상 수업
- 사내 SSO 연동
- 퍼블릭 클라우드 배포 (초기엔 로컬 서버)
- 기존 사내 시스템(Jira/문서 등) 연동
- 복잡한 증서 발급·검증 시스템

## 첫 슬라이스 (Walking-Skeleton 후보, Q4=A)

멘토가 코호트 개설(정원 설정) → 멘티가 **선착순 자동 참여** → (정원 마감 시 관리자 점검) 까지 얇게 끝까지 도는 흐름.
로그인/회원가입은 이 흐름을 받치는 최소 형태로 함께 포함.

## 가정 & 오픈 이슈 (Assumptions & Open Items)

- (가정) "정원 마감 시 관리자 수동 점검·승인"은 초과 신청 대기/재확인 용도이며, 평시 참여는 승인 불필요.
- (가정) 시스템 관리자와 운영 담당자는 동일 역할로 취급(별도 분리 필요 시 requirements에서 조정).
- (오픈) 최종 보고서의 형식(자유 서식 vs 템플릿)과 증빙자료 파일 형식/용량 제한은 requirements/functional-design에서 확정.
- (오픈) "정산 조건"의 구체 정의(무엇을 충족해야 정산 조건 충족인지)는 requirements에서 확정.
